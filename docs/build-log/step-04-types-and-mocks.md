# Step 04 — Types, API client, TanStack Query hooks, MSW mock backend

Cocoon now has a working data layer, even though we haven't built a backend.
Every endpoint in SPEC §5 has a TypeScript type, a hook you can call from a
React component, and a mock that returns realistic fixture data. The rest of
the frontend (steps 5–13) is built against this layer; when the real Hono
server lands in steps 15–17, flipping `VITE_USE_MOCKS=false` is the only
change the UI needs.

## What was built

- **`src/lib/types.ts`** — every request / response shape in SPEC §5, with
  cross-references to the spec in comments. No runtime code so the real
  Hono server can import the exact same file in step 17.
- **`src/lib/api.ts`** — a typed `fetch` wrapper. `api.get<T>()`,
  `api.post<Req, Res>()`, `api.patch`, `api.put`, `api.multipart`. Attaches
  `Authorization: Bearer <token>` from the session, and throws `APIError`
  (a real `Error` subclass with `.code` and `.status`) on non-2xx.
- **`src/lib/auth.ts`** — minimal mock-only auth. When
  `VITE_USE_MOCKS=true`, `getSession()` returns a hard-coded test user with
  token `'mock-dev-token'`. Step 5 will add sign-in / sign-out; step 15
  swaps in Supabase.
- **`src/mocks/fixtures.ts`** — the 6 English fixture entries from mockup
  `05-past-entries`, including the locked entry with passcode **1234**.
- **`src/mocks/db.ts`** — in-memory store around the fixtures. Pure TS,
  no HTTP, enforces every SPEC rule (max 2 photos per entry, 5-tries lockout,
  60-s test-reminder cooldown). Easy to unit-test.
- **`src/mocks/handlers.ts`** — MSW handlers for every SPEC §5 route.
  `POST /api/transcribe` and `POST /api/entries` each wait 2 s to simulate
  real OpenAI + Claude calls (per the step prompt).
- **`src/mocks/browser.ts`** and **`src/mocks/server.ts`** — the two MSW
  setups (`setupWorker` for the browser via the service worker,
  `setupServer` for Vitest + Node).
- **`src/hooks/queries.ts`** — one TanStack Query hook per endpoint
  (`useMe`, `useEntries`, `useEntry`, `useCalendar`, …). Mutations
  invalidate the right query keys so the UI always shows fresh data after
  a write.
- **`src/components/dev/DevEntriesProbe.tsx`** — a dev-only unstyled list
  on Home. Confirms the stack works end-to-end. Step 7 deletes it.
- **`.env.local`** — local switch `VITE_USE_MOCKS=true`. Gitignored.

## Explanations

### Types (`src/lib/types.ts`)
- **What it is.** Every request / response shape in SPEC §5, plus the core
  DB rows from §4 (`Profile`, `Entry`, `Photo`, `CalendarDay`, `Reminder`).
- **Why.** One file to change if SPEC changes. Both the browser and the
  server will import these so they can't drift.
- **How it connects.** Hooks, API client, MSW handlers, and (soon) the
  Hono server all import from here.
- **Worth knowing.** `EntrySummary` is a discriminated union
  (`is_locked: true | false`). TypeScript forces callers to check the flag
  before touching title / mood / photos — the type literally can't let a
  component leak locked content.

### API client (`src/lib/api.ts`)
- **What it is.** A thin typed wrapper around `fetch`. Reads the bearer
  token from `getSession()`, parses JSON, throws `APIError` on non-2xx.
- **Why.** Every component uses the same auth / error / JSON plumbing.
  Changing the base URL or auth scheme in the future is a one-file edit.
- **How it connects.** Hooks call `api.get` / `api.post` etc.
- **Worth knowing.** `APIError extends Error` with `.code: ApiErrorCode`,
  so components can branch on `err.code === 'locked'` or
  `'wrong_passcode'` without magic numbers.

### Mock auth (`src/lib/auth.ts`)
- **What it is.** Two tiny functions: `getSession()` and `isSignedIn()`.
- **Why.** Something has to tell the API client "you're signed in as X"
  before step 15's real Supabase arrives. Mocks make that one line: always
  the test user.
- **How it connects.** `api.ts` calls `getSession()` to set the Authorization
  header. Sign-in page (step 5) will replace this file with real sign-in /
  sign-out; the API client doesn't change.

### TanStack Query hooks (`src/hooks/queries.ts`)
- **What they are.** One hook per endpoint. Queries wrap `useQuery`,
  mutations wrap `useMutation`.
- **Why.** TanStack Query handles caching, de-duplication, retries,
  loading / error states — our pages stay thin.
- **How they connect.** Query keys are tuples
  (e.g. `['entry', id]`, `['entries', cursor ?? null]`) so mutations can
  invalidate the right scope precisely.
- **Worth knowing.** `useCreateEntry` invalidates both the entries list
  and the calendar so the new entry shows up without a reload.

### MSW mock backend (`src/mocks/`)
- **What it is.** Four files that intercept every `/api/*` request and
  serve from an in-memory map of fixture entries.
- **Why.** We can build the entire UI journey (steps 5–13) without a
  backend, and without worrying about Supabase or AI API rate limits.
- **How it connects.** `src/main.tsx` dynamically imports the browser
  worker and starts it only when `VITE_USE_MOCKS === 'true'`. The dynamic
  import means MSW doesn't get bundled when mocks are off (production).
- **Worth knowing.** The real Hono server in step 17 will implement the
  same rules — locked entries return 423, the 5-tries lockout returns 429,
  etc. — so this mock is a faithful stand-in. `src/mocks/db.ts` has unit
  tests that lock those rules in.

### Dev entries probe (`src/components/dev/DevEntriesProbe.tsx`)
- Temporary, dev-only, deliberately unstyled. Deletes in step 7 once the
  real past-entries card lands. Proves the full stack (hook → api → fetch →
  MSW handler → db) works end-to-end.

## How to try it

```bash
# .env.local already has VITE_USE_MOCKS=true
npm run dev
# http://localhost:5173 — Home card now shows a "Dev probe · past entries"
# section with 6 entries and mood badges.
# DevTools → Network → filter to Fetch/XHR: you'll see /api/entries,
# /api/me etc. handled by the Service Worker (MSW).

npm run typecheck   # green
npm run lint        # green
npm test            # 31 tests pass across 4 files
npm run build       # production build (MSW excluded)
npm run shots       # 10 PNGs — Home now shows the fixture list
```

## Notes to Aruna

- Mockup entry #3 was Tamil; I translated the whole scene to English as
  "A Cake for Mum" with a cake placeholder photo.
- Mockup entry #2's mood looked ambiguous — I used `tired` (lavender). If
  you want `relieved` instead, one-line fix in
  `src/mocks/fixtures.ts`.
- The locked entry's passcode is `1234`. The real server in step 17 hashes
  passcodes with PBKDF2 (210 000 iterations); the mock compares plaintext.
- Photos use `picsum.photos` seeded URLs — stable but external. If you're
  offline the placeholders won't load, but the probe still shows titles.
- `useCreateEntry` and `useTranscribe` each take 2 s in the mock to
  simulate the real AI calls. Step 7's recording flow will show the
  "Listening back carefully…" and "Writing your entry…" states during
  that window.
- When mocks are off (`VITE_USE_MOCKS=false`), every `/api` call 404s
  because we have no real backend yet. That's expected until step 15.
- Mock auth means the browser is **always signed in** as the test user.
  The sign-in page and route guards arrive in step 5 — the first thing
  that step does is replace `src/lib/auth.ts`.
